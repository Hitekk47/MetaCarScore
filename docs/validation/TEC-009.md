# TEC-009 — Déduplication Supabase entre métadonnées et pages

Vérification du 21 octobre 2026. Branche `fix/tec-009-supabase-request-cache`,
créée depuis `origin/main` à `9b64d901fb378bf578bd6a3ad3da4289b037dc05`.
Aucun changement de TEC-008 n'a été repris d'une branche de travail.

## Résultat mesuré

Sur `/chery/tiggo-7/2024/tiggo-7`, **6 → 4 appels Supabase par rendu**
(−33,3 %), dont **4 → 2 RPC POST** (−50 %).
Les six requêtes HTTP successives de chaque version donnent ce même décompte.

| Appel effectivement transmis | Avant | Après |
| --- | ---: | ---: |
| POST `get_full_context_by_slugs_v3` | 2 | 1 |
| POST `get_vehicle_seo_stats_v5` | 2 | 1 |
| GET `model_aliases` | 1 | 1 |
| GET `reviews` | 1 | 1 |
| Total | 6 | 4 |

React compare les arguments objets par identité : les objets reconstruits par
`generateMetadata` et la page empêchaient le partage de leurs RPC. Cependant,
Next dédupliquait déjà les GET identiques de `getReviews` et `getModelAliases`,
y compris la lecture d'alias commune. Aucun gain réseau supplémentaire n'est
démontré pour une conversion de ces deux helpers aux arguments primitifs.

## Protocole serveur

- Node 24.19.0, Next 16.3.0, React 19.2.8 et Supabase JS 2.112.2,
  issus des dépendances installées et du verrou npm.
- Avant : code de `9b64d90`. Après : même base avec seulement les deux wrappers
  de requêtes modifiés. Compilation de production avec
  `npm run build -- --webpack`, puis `npm run start -- --hostname 127.0.0.1 --port 3000`.
- Une sonde préchargée par `NODE_OPTIONS=--require=.../trace-fetch.cjs` enveloppe
  le `globalThis.fetch` original **avant** que Next installe son propre wrapper.
  Elle filtre l'hôte Supabase, enregistre méthode, chemin, paramètres, statut et
  SHA-256 de la réponse. Elle n'enregistre aucun en-tête ni clé de connexion.
  Les appels absorbés par les caches Next/React n'atteignent donc pas la sonde.
- Des requêtes HTTP réelles vers Next sont exécutées en série, sans navigateur
  ni préchargement de liens, avec `redirect: 'manual'`. Chaque réponse est lue
  intégralement avant de délimiter la mesure suivante. Tous les appels Supabase
  de la fiche représentative répondent 200.
- Le build classe les fiches en `ƒ` (rendu serveur à la demande). Les réponses
  portent `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate`,
  sans `x-nextjs-cache`. Les nouvelles requêtes HTTP exécutent à nouveau 6 puis
  4 appels : aucun résultat de page déjà servi ne masque le décompte.
- La mémoïsation GET observée correspond à `dedupe-fetch` de Next. Le client
  Supabase installé ne fournit pas d'`AbortSignal` par défaut. Les POST ne sont
  pas éligibles à cette mémoïsation. Les options de cache n'ont pas été changées.
- Les données proviennent de lectures publiques autorisées et des deux RPC de
  lecture existantes. Aucun déploiement, écriture SQL ou migration n'a été lancé.

Le benchmark historique `scripts/benchmark-db-calls.ts` simule une latence et un
cache Map ; il n'est pas utilisé pour établir les résultats de cette vérification.

Deux particularités expliquent les décomptes restants :

- La page MY passe `p_my: 2024` au contexte, tandis que ses métadonnées omettent
  `p_my`. Ce sont deux clés distinctes, conservées pour respecter les paramètres
  et leur éventuelle influence sur les alias ; seule la RPC SEO est dédupliquée.
- Une redirection déclenche un rendu RSC de récupération par Next, qui recalcule
  les métadonnées avec un nouveau cache React. Le code installé de `app-render`,
  `metadata` et du renderer RSC confirme cette nouvelle portée. Des appels restent
  donc exécutés dans ce second rendu, même sans suivre la redirection HTTP.
  La correction ne crée aucun cache partagé entre ces rendus.

## Changement et contrôles

`getFullContext` et `getVehicleSeoStats` gardent leurs signatures publiques à
objet. Chacune délègue à une fonction privée `cache()` utilisant les valeurs
primitives dans un ordre fixe : cinq dimensions pour le contexte, quatre pour
le SEO. MY, modèle et motorisation restent distincts ; aucune chaîne n'est
normalisée. `undefined` reste omis lors de la sérialisation Supabase. Les versions
RPC, erreurs et valeurs de retour sont conservées.

Le calcul des essais, les alias familiaux, les filtres MY/motorisation et les scores
ne changent pas. Aucun cache persistant, TTL ou option `fetch` n'est ajouté ; tous
les `revalidate = 3600` restent inchangés.

- `node scripts/test-query-cache.mjs` : passe. Il charge le vrai `queries.ts`
  dans le renderer RSC de Next avec la condition React serveur ; seul Supabase
  est simulé. Déduplication concurrente, toutes les dimensions de clé, absence
  versus `undefined`, chaînes vides et zéro, isolation entre rendus, corps/versions
  RPC, erreurs et résultats vides sont vérifiés. Le test échoue sur le code initial
  avec 2 RPC de contexte au lieu d'une. Il n'appelle pas `cache()` hors rendu pour
  conclure à sa mémoïsation et ne remplace pas React par un cache simulé.
- Tests Bun ciblés : **38 passent**, 0 échec, sur `queries.test.ts`,
  `phase4-queries.test.ts`, `seo-utils.test.ts` et `utils.test.ts`.
- TypeScript applicatif, compilation de production et lint des fichiers de code
  ajoutés/modifiés : passent. `git diff --check` passe.
- Lint global : **6 erreurs préexistantes** `no-explicit-any` dans
  `src/app/[marque]/page.tsx` et `src/lib/utils.test.ts`, et 7 avertissements.
  Ces fichiers ne sont pas modifiés par TEC-009.
  Ce constat est historique : les derniers problèmes de lint sont corrigés dans
  la [PR #98](https://github.com/Hitekk47/MetaCarScore/pull/98).

## Temps et limites

Temps HTTP jusqu'à lecture complète du HTML, sonde activée dans les deux versions :

- Avant : 950, 535, 520, 608, 481, 512 ms.
- Après : 802, 476, 509, 496, 510, 446 ms.

Après exclusion du premier rendu de chaque processus, les médianes sont
**520 → 496 ms**, avec des étendues **481–608** et **446–510 ms**.
Ces petits échantillons successifs traversent le réseau et le proxy et ne sont
pas alternés. Le gain de temps n'est pas établi avec assez de fiabilité pour
annoncer une accélération ; la réduction d'appels, elle, est reproductible.

Les mesures portent sur le serveur Next local compilé avec webpack et les données
hébergées accessibles au moment du test, sans accès aux journaux internes de
PostgreSQL ni mesure Vercel. Elles comptent les requêtes HTTP Supabase qui
atteignent le transport et obtiennent une réponse, pas les requêtes SQL internes.
Elles ne prouvent pas toutes les combinaisons d'alias ni la qualité des données.
Le contrat futur de mémoïsation devra être revérifié si Next, le client Supabase
ou ses options de timeout/`AbortSignal` évoluent.
